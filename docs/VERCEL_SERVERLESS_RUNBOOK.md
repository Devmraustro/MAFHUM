# Vercel serverless operations runbook

Operating MAFHUM on Vercel Functions. This runbook is about *how the pieces
fit in production*; the phase checklist (`docs/VERCEL_MIGRATION_PHASES.md`)
tracks what is implemented, and `docs/NEON_DATABASE_RUNBOOK.md` covers the
database in depth.

Everything marked **OWNER ACTION** requires credentials or paid resources
this migration was not authorized to create. Nothing below was executed
against a real deployment.

## 1. Architecture on Vercel

| Concern | Container | Serverless (Vercel) |
| --- | --- | --- |
| API process | `uvicorn` long-running | Function per request (`vercel_app.py`, `start_worker=False`) |
| Background processing | resident worker thread pool | **processing tick** (Phase F): frontend fires one after upload/retry; `.github/workflows/processing-tick.yml` every 5 min once configured |
| Uploads > 4 MiB | single request (≤ `MAX_UPLOAD_MB`) | **chunked upload sessions** (Phase E): each request ≤ `UPLOAD_PART_SIZE_BYTES` |
| Database | PostgreSQL (any host) | Neon PostgreSQL (pooled endpoint) |
| Object storage | local private filesystem | Vercel Blob (`STORAGE_BACKEND=vercel_blob`) |
| Malware scanning | local clamd | **external clamd host — BLOCKED** (see §6) |
| Migrations | container entrypoint step | explicit `alembic upgrade head` against the direct (non-pooled) endpoint |

The serverless entrypoint forces the *declared* `processing_worker_enabled`
to `False` (matching the code-level `start_worker=False`), so the tick can
never be wedged by a stale env var.

## 2. Environment variables (owner sets; see `.env.example` for the full list)

Required for the serverless path:

| Variable | Value | Notes |
| --- | --- | --- |
| `DATABASE_URL` | `postgresql+psycopg://…-pooler.…neon.tech/…?sslmode=require` | pooled endpoint for the Functions; keep pool size small (`DB_POOL_SIZE=1..2`) |
| `SESSION_SECRET` | ≥ 32 random chars | generated by the owner |
| `STORAGE_BACKEND` | `vercel_blob` | |
| `BLOB_READ_WRITE_TOKEN` | `vercel_blob_rw_…` | per-store token; owner creates the store |
| `PROCESSING_WORKER_ENABLED` | `false` | the tick is the driver |
| `MALWARE_SCAN_REQUIRED` | `true` | fail-closed: uploads refuse without a CLEAN verdict |
| `CLAMD_UNIX_PATH` / `CLAMD_TCP_HOST` | external scanner address | see §6 |
| `METRICS_SCRAPE_TOKEN` | ≥ 32 random chars | scrapes `/api/v1/admin/metrics` |
| `PROCESSING_TICK_TOKEN` | ≥ 32 random chars | enables `POST /api/v1/processing/tick-scheduler` for the scheduled workflow |
| `APP_ENV` | `production` | turns on production assertions (`assert_production_ready`) |

Migration connections (release step only) use the **direct** endpoint
(`…neon.tech/…` without `-pooler`) — advisory locks and `CREATE INDEX
CONCURRENTLY`-style operations must not go through a pooler.

## 3. Deployment sequence (owner)

1. Provision Neon (see `docs/NEON_DATABASE_RUNBOOK.md`) — pooled + direct
   connection strings.
2. Provision the Vercel Blob store; copy the read-write token.
3. Set the environment variables above on the Vercel project (preview and
   production scopes).
4. **Migrations as a release step:** from a trusted machine
   `DATABASE_URL=<direct endpoint> alembic upgrade head` (downgrade is
   tested in CI on every push: upgrade→downgrade→upgrade).
5. Deploy; verify `GET /health/ready` returns `ok` (it will report
   `processing_worker: stopped` — on serverless that is the *honest*
   state; the tick is the driver).
6. Configure the scheduled tick (§4).
7. Smoke: register a user, upload a small PDF (direct path), upload a > 4 MiB
   PDF (chunked path), watch the document reach `ready` after the tick, ask a
   grounded study question, generate a deck.

## 4. Scheduled processing tick

- Workflow: `.github/workflows/processing-tick.yml` (every 5 minutes).
- It self-skips until the owner sets repository **`vars.MAFHUM_API_URL`**
  and **`secrets.PROCESSING_TICK_TOKEN`** (the same value as the
  deployment's `PROCESSING_TICK_TOKEN`).
- Frequency choice: GitHub Actions' minimum schedule interval (5 min). The
  frontend also ticks on upload/retry, so interactive latency does not
  depend on the schedule; the schedule is the safety net for API-only
  clients and abandoned tabs.
- Ticks are idempotent and bounded (`PROCESSING_TICK_MAX_JOBS`,
  `PROCESSING_TICK_BUDGET_SECONDS`); overlapping runs cannot double-process
  (exclusive `SKIP LOCKED` claims).

## 5. Monitoring and alerting

Scrape `GET /api/v1/admin/metrics` with `Authorization: Bearer
$METRICS_SCRAPE_TOKEN` (Prometheus text format). Suggested alerts:

| Signal | Alert when |
| --- | --- |
| `mafhum_up` | `0` (scrape failing) |
| `mafhum_processing_driver{mode=…}` | mode is not what the deployment intends |
| `mafhum_processing_pending` + `mafhum_processing_jobs_total{status="queued"}` | queue depth grows monotonically over ~30 min (ticks not draining) |
| `mafhum_processing_jobs_total{status="failed"}` | any sustained increase (inspect `error_code` on documents) |
| `mafhum_upload_sessions_total{state="pending"}` | sustained growth with no `assembled` (clients abandoning uploads; expiry reclaims them, growth means something systemic) |
| `mafhum_malware_scanner_available` | `0` while `malware_scan_required=1` — uploads are being refused (fail-closed) |
| `mafhum_audit_denied_total` | sharp increase (probing or a broken client) |

Readiness (`/health/ready`) degrades honestly: database, storage
writability, worker state, and scanner availability when scanning is
mandatory. Correlation: every error response carries `request_id`, which is
also recorded on audit events and structured log lines (`LOG_FORMAT=json`).

## 6. Known limitations on serverless (honest list)

- **ClamAV cannot run on Vercel.** The daemon needs a resident process and
  a mutable signature volume. With `MALWARE_SCAN_REQUIRED=true` and no
  reachable scanner, uploads fail closed — that is the intended safe
  behavior. Options for the owner: an external clamd host reachable from
  the Functions, or routing uploads through a scanning sidecar. Until one
  exists, a real serverless deployment cannot accept uploads; this is the
  single hard blocker for production traffic.
- **Hobby cron is daily-only**; that is why the scheduled tick lives in
  GitHub Actions (5-minute minimum) and the frontend ticks interactively.
- **Function execution budget**: the tick's default 25 s budget fits the
  default Function timeout; if the owner raises the timeout, raise
  `PROCESSING_TICK_BUDGET_SECONDS` to match.
- **Body limit**: the chunked path keeps every request ≤
  `UPLOAD_PART_SIZE_BYTES` (4 MiB default) — under the ~4.5 MB platform
  limit — but `MAX_UPLOAD_MB` still bounds total document size (20 MB
  default).
- **Direct-to-Blob browser uploads are not available** from the Python SDK
  (no client-token minting in `vercel-blob==0.5.0`); the API-mediated
  chunked path is the designed equivalent.

## 7. Incident playbook

- **Documents stuck `pending`**: `POST /api/v1/processing/tick` (any
  authenticated client) or check the scheduled workflow's runs; check
  `mafhum_processing_driver`; check database reachability.
- **Stuck `processing` after a crash**: the next tick's
  `recover_stale_jobs` requeues them (heartbeat-based, attempt-bounded).
- **Abandoned chunked uploads**: sessions expire
  (`UPLOAD_SESSION_TTL_MINUTES`, 24 h default); the next tick deletes
  their stored parts. `mafhum_upload_sessions_total{state="pending"}`
  shows the backlog.
- **Blob store suspended/quota**: writes fail with `StorageError`; uploads
  refuse cleanly. Owner action in the Vercel dashboard.
- **Suspected bad release**: `alembic downgrade` is tested, but treat it as
  a rollback of schema, not of data — take a branch backup first (Neon
  branching, see the database runbook).
